# ADR-0002: Date representation, tables and performance

- Status: Accepted
- Date: 2026-09-25 (rewritten 2026-10-07 after measuring the alternatives)
- Deciders: Sanam Pakuwal

## Context

Performance is the first requirement of the family (hub decision, 2026-10-07): the Go port must
be the fastest Go library for Bikram Sambat and, per `shared/spec/BENCHMARK.md` §6, within 1.5
times C# NepDate on B1, B2 and B7 with zero bytes allocated per operation.

C# NepDate (commit `cb05cb65`) gets its speed from flat static arrays: `NepaliToEnglish.data`
(3588 tuples: BS month length and the AD date of the month's last day) and
`EnglishToNepali.data` (3589 tuples), so BS → AD is one array read plus `DateTime.AddDays`, and
AD → BS is one read plus a short walk back. Its patro lookups binary-search sorted `ushort`
day-offset arrays, but `GetCalendarInfo`, `EventsNp` and `EventsEn` allocate new `string[]` on
every call. The algorithm we must reproduce is `shared/spec/ALGORITHM.md`; how a port stores the
tables is its own choice, the results are not.

Every Go competitor walks the calendar year by year or uses maps and `fmt`
(`docs/competitors.md`). Go's own `time` package uses no month tables at all since Go 1.23: it
computes Gregorian dates with Neri and Schneider's Euclidean affine functions
(`src/time/time.go`; https://doi.org/10.1002/spe.3172). BS month lengths follow no formula, so we
need tables on the BS side; the question was which tables, and whether to use formulas or tables
on the AD side. We measured instead of guessing (§8).

## Decision

### 1. `Date` is `struct{ year uint16; month, day uint8 }` (4 bytes)

- Comparable with `==`, usable as a map key, chronological when compared field by field, and
  readable in a debugger. Passed and returned in registers (Go's register ABI, Go 1.17+).
- The zero value `{0, 0, 0}` is "no date" (PARITY D-01); `IsZero` checks `year == 0`.
- Rejected: an `int32` serial (with +1 so the zero value stays "no date"). It makes B2 cheaper
  only until the caller reads `Year()`, `Month()` or `Day()`, which then costs the same search:
  measured 8.8 ns for B2 including the field reads against 5.7 ns for the field struct, and 10.1
  ns against 6.8 ns for B1. Rejected too: a struct carrying both fields and the serial (8 bytes),
  because every constructor would pay for the serial whether or not it is used.

### 2. Tables are generated Go arrays of integer constants

Generated by `internal/gen` from `shared/data/` (ADR-0001 §5). Core, in `calendar_gen.go`:

| Table | Type | Bytes | Content |
|---|---|---|---|
| `bsMonthStart` | `[3589]int32` | 14,356 | serial (ALGORITHM §2) of the first day of BS month `k = (y-1901)*12 + m-1`; entry 3588 = 109212 |
| `adMonthStart` | `[3601]int32` | 14,404 | serial of the first day of AD month `k = (y-1844)*12 + m-1`, AD 1844-01 to 2144-01 (negative before the epoch) |

Month length is `bsMonthStart[k+1] - bsMonthStart[k]` and a year's start is
`bsMonthStart[12*i]`, so the spec's `PACKED` and `YEAR_START` (ALGORITHM §2) are not stored: they
are derived views of the same numbers. 28.8 KB in total, against about 115 KB for C#'s two tuple
tables.

Patro, in `patro/patro_gen.go` only (hub ADR-0004; the core has none of these):

| Table | Type | Bytes | Content |
|---|---|---|---|
| `dayInfo` | `[2793]uint32` | 11,172 | one record per day from 2077-01-01 (serial 64285) to 2084-08-20 (67077): bits 0–5 tithi name id + 1, bit 6 public holiday, bits 7–10 event count, bits 11–22 first index in `eventName` |
| `eventName` | `[3032]uint16` | 6,064 | name ids of every event, day by day, in file order |
| `nameOff` | `[1507]uint32` | 6,028 | byte offsets into `nameText`; pair `i`, language `l` is `nameText[nameOff[2i+l]:nameOff[2i+l+1]]` |
| `nameText` | `string` constant | 59,800 | the 753 deduplicated (en, np) name pairs, tithi names first |

PATRO §3 suggests sorted serials and binary search for holidays and events, and allows dense
per-day tables when a port's benchmark shows they are faster at an acceptable size. We measured
both (§8): the sparse layout (a per-day tithi byte, 294 sorted holiday serials, 1671 sorted
event-day serials with a start and a count each) takes about 15.7 KB and 22.6 ns per date for B7;
the dense `dayInfo` record takes 11.2 KB and 4.7 ns in the same run. Dense is smaller because one
`uint32` per day replaces three parallel arrays over 1671 event days, and every patro query becomes
one subtraction, one bounds check and one array read. The generator fails when the data outgrows a
bit field (G4-01).

### 3. Conversions: one table read plus one correction, in both directions

- `toSerial(d) = bsMonthStart[k] + day - 1`.
- `fromSerial(s)`: estimate the month index as `k = (s*34443 - 262144) >> 20` (34443 / 2^20 is
  about 1 / 30.44, the mean BS month length), then `if bsMonthStart[k+1] <= s { k++ }`. The
  generator searches for the multiplier and offset and checks that for **every** serial
  0..=109211 the estimate is the true index or one below it; it refuses to write constants that
  fail. Year, month and day then come from `k / 12`, `k % 12 + 1` and `s - bsMonthStart[k] + 1`.
- AD side, mirrored: `FromGregorian` reads `adMonthStart[(y-1844)*12 + m-1] + d - 1` (after the
  Gregorian validity and year-range checks, ALGORITHM §3); `Gregorian()` estimates the AD month
  with `k = (s*34443 + 3342336) >> 20` and the same one-step correction on `adMonthStart`.
- No loop, no binary search, no division by a variable; `toSerial`, `fromSerial` and the AD
  estimate each fit Go's inlining budget of 80 (`-gcflags=-m=2` reports costs 22, 62 and 49).
- The literal ALGORITHM §4 and §5 functions (binary search over year starts, Hinnant's
  `days_from_civil` and `civil_from_days`) live in `reference_test.go` as the oracle, and the
  exhaustive test (G1-07) compares the fast path with them for all 109,212 days.

### 4. Static data, no start-up work

A package-level array initialised with a composite literal of constants is laid out by the
compiler as static data (`cmd/compile/internal/staticinit`); no code runs at start-up. Measured on
a probe binary built with Go 1.27.1 for windows/amd64 (`go tool nm -size`):

- the `int32`/`uint16`/`uint32` tables sit between `runtime.noptrdata` and `runtime.enoptrdata`:
  file-backed, paged in on first touch, never scanned by the garbage collector;
- the bytes of `nameText` sit in `.rdata` (`go:string.*`);
- the package has no `init` function symbol;
- tables the program never references are removed by the linker (the probe kept only the
  tables it used), which is also why a core-only binary links no patro data.

Go has no read-only package variables, so the tables live in `.noptrdata`, not `.rdata`; nothing
in the package writes to them, and `TestConcurrentReads` (ADR-0004) runs under `-race`.

Rejected: `//go:embed` of the JSON or a binary blob (parsing or decoding at start-up, and
`encoding/json` in every binary); `map` tables (start-up cost, hashing on every lookup, as nepcal
and GoBikramSambat do); a `[753][2]string` name table (24,096 bytes of string headers in `.data`,
which the garbage collector scans as roots on every cycle, and measured 7.4 against 6.7 ns per
date in B7).

### 5. Zero allocation, asserted by tests

These allocate nothing, checked with `testing.AllocsPerRun` (ADR-0004) and `-benchmem` (G5):

- `New`, `FromGregorian`, `FromTime`, every accessor, `Gregorian`, `Weekday`, `YearDay`,
  `Compare`, `Before`, `After`, `AddDays`, `AddMonths`, `AddYears`, `DaysUntil`, `Diff`, `Next`,
  `Prev`, the fiscal and range functions, and ranging over `Range.Days()`;
- `AppendShort`, `AppendLong`, `AppendFormat`, `AppendText`, `Lang.AppendDigits` into a slice
  with enough capacity, and every `Name`/`ShortName` (they return constants or substrings of a
  constant);
- a successful `Parse`, `ParseLenient` and `UnmarshalText`;
- `patro.Of`, `Info.Tithi`, `IsPublicHoliday`, `EventCount`, `Event(i)`, `Tithi.Name`,
  `Event.Name`, `Coverage`, and ranging over `Info.Events()` and `PublicHolidays()`.

`String`, `Short`, `Long`, `Format` and `MarshalText` allocate exactly the returned value. A
failed parse allocates the `*ParseError` (and, from `[]byte`, its `Input` copy).

### 6. Hot-path rules (what breaks zero allocation in Go)

Verified with `go build -gcflags=-m` on the prototype; see the Go FAQ, "How do I know whether a
variable is allocated on the heap or the stack?" (https://go.dev/doc/faq#stack_or_heap):

- No `fmt`, `strconv.Itoa`, `strings.Builder` or `bytes.Buffer`: `fmt` takes `...any`, and
  converting a non-constant value wider than a byte to an interface allocates.
- No `any` or interface parameters in hot paths. Errors are the package-level sentinels of
  ADR-0003 (pointers, so returning one doesn't allocate).
- Formatting appends to the caller's slice. String-returning methods use a `[96]byte` stack buffer
  and convert once. (When the result does not escape, the compiler even keeps that string on the
  stack: `String()` measured 0 B/op in a benchmark that only read its length.)
- Parsing is one unexported generic function over `string | []byte`, so `UnmarshalText` never
  converts `string(b)` up front. Measured: parsing through `string(b)` costs 1 allocation per
  call, because the string escapes into `*ParseError.Input`; the generic version costs 0.
- Iterators (`iter.Seq`) allocate their closure unless the call is inlined into the `range`
  statement. `Info.Events()` and `Range.Days()` are kept small enough to inline (measured 0
  allocations), and `Info.EventCount()` plus `Info.Event(i)` give an index loop that needs no
  closure at all (measured 6.7 against 10.3 ns per date for B7).
- No `[]rune` conversion and no `unicode/utf8` loops: Devanagari digits are the three bytes
  `0xE0 0xA5 0xA6+d`.
- No `map`, no `sync.Mutex`, no lazy initialisation in the core. The only `sync.OnceValue` is the
  `Asia/Kathmandu` location in `Today(nil)` (G4-05), outside every benchmark.

### 8. Measurements behind this decision

Prototype code: the experiment folder of the planning session (not in the repository). Go 1.27.1,
windows/amd64, on the reference machine (i5-12500H, Windows 11, Ultimate Performance), the test
binary started with `start "" /high /affinity 4` (logical CPU 2). Go numbers are medians of 10 runs
(`-test.benchtime=300ms -test.count=10`), every run within 7 % of the median; the last full run was
on 2026-10-08. Inputs are the BENCHMARK §2 and §3 dates. The C# column is the .NET 10 column of the
hub's `docs/benchmarks/dotnet.md` (BenchmarkDotNet 0.15.8, NepDate 2.0.7, same machine and
affinity, rerun 2026-10-09 with no other jobs). ns per operation (one
operation is one date, except B8, where it is one whole month grid in both columns):

| ID | Go prototype (chosen design) | B/op | C# NepDate | C# B/op | Go / C# |
|---|---|---|---|---|---|
| B1 BS → AD | 6.8 | 0 | 13.29 | 0 | 0.51 |
| B2 AD → BS | 5.6 | 0 | 18.64 | 0 | 0.30 |
| B3 add 1000 days | 4.6 | 0 | 17.50 | 0 | 0.26 |
| B4 add 13 months | 4.2 | 0 | 18.85 | 0 | 0.22 |
| B5 long, Nepali, weekday | 30.6 (`AppendLong`), 58.0 (string) | 0, 1 alloc | 153.02 | 435 | 0.20, 0.38 |
| B6 strict parse | 17.8 (ASCII-only prototype) | 0 | 21.55 | 0 | 0.83 |
| B7 patro info | 6.7 (`Event(i)` loop), 10.3 (`range Events()`) | 0 | 47.93 | 51 | 0.14, 0.21 |
| B8 month grid | 226 | 0 | 3,133 | 1,429 | 0.07 |

The BENCHMARK §6 release blocker for Go (B1, B2, B7 within 1.5 times C#, so under 19.9, 28.0 and
71.9 ns) has a margin of 2.9 times on B1, 5.0 on B2 and 7.0 on B7 (with `range Events()`)
in the prototype. A Stopwatch harness over the same NepDate
sources, run back to back with Go on 2026-10-07, gave C# 17.5, 27.4 and 65.3 ns for B1, B2 and B7;
BenchmarkDotNet's numbers above are lower, and the table uses them.

Alternatives measured for B1 and B2 (same run, ns per date):

| Variant | B1 | B2 |
|---|---|---|
| ALGORITHM §4–5 literally (month loop, binary search over year starts, Hinnant) | 23.3 | 24.9 |
| packed lengths with popcount instead of the month loop, Hinnant | 19.8 | n/a |
| `bsMonthStart` + Hinnant | 17.1 | n/a |
| `bsMonthStart` + Neri–Schneider (Go `time` style) | 10.3 | 8.5 (estimate on the BS side) |
| binary search over `bsMonthStart` (12 steps) | n/a | 21.5 |
| C#-style direct tables (BS month → AD date, AD month → BS date, then step) | 6.5 | 5.7 |
| **chosen:** `bsMonthStart` + `adMonthStart`, estimate + one correction both ways | **6.8** | **5.6** |

Alternatives measured for B7 (a separate run on 2026-10-08, same command and affinity; this run
was about 30 % faster across the board than the one above, so compare within the table only):

| Variant | B7 ns per date |
|---|---|
| PATRO §3 sparse layout: tithi byte per day, binary search over 294 holiday and 1671 event-day serials | 22.6 |
| dense `dayInfo`, `range Info.Events()` | 7.7 |
| dense `dayInfo`, names from a `[753][2]string` table | 5.5 |
| **chosen:** dense `dayInfo`, `EventCount()` + `Event(i)`, names sliced from one string constant | **4.7** |

The C#-style direct tables tie with the chosen design but need two more tables (28 KB) and a
Gregorian month-stepping loop with the leap-year rule; the chosen design reuses one estimate step
in both directions. Affinity matters on this CPU: the same B1 benchmark measured 4.5 to 5.8 ns
per date on logical CPUs 0 to 7 (performance cores) and 9.9 to 16.1 ns on CPUs 8 and up
(efficiency cores); without `/high`, background load on CPU 2 gave up to ±75 % variation.

## Consequences

- Every core operation is a handful of instructions and at most three cache lines; B1 to B8 of
  the prototype run 1.2 to 14 times faster than C# NepDate (BenchmarkDotNet baseline) on the same
  machine.
- The generator owns two derived facts (the estimate constants and the patro bit-field limits)
  and verifies both, so a data update can't break them silently.
- `reference_test.go` keeps the spec's own algorithm in the repository, so reviewers compare the
  spec with Go line by line, and the fast path is proved equal to it on every day of the range.
- `docs/API.md` gains `patro.Info.Event(i)` for the closure-free loop.
